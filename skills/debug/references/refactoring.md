# 구조 리팩터링 — 동작은 그대로, 구조만 바꾼다

동작을 바꾸지 않는 이동·이름 변경·분리·통합 작업에서 읽는다. 동작 변경이 섞이면 그 부분은 SKILL.md 본 절차를 따른다.

## 1. 착수 전

- **동작 기준선과 외부 계약을 먼저 고정한다.** 이동 후 테스트가 통과해도 기준선과 다른 동작이면 회귀다.
- 승인된 목표 구조가 있으면 다시 설계하지 않는다. 없으면 목표 구조를 먼저 합의·기록한다.
- 다음 표를 만든다.
  - 파일별 이동표: 현재 경로 → 목표 경로
  - import 소비자표: 각 이동 대상을 가져다 쓰는 곳
  - 경로 리터럴·CI·외부 스크립트·문서 명령 영향표

## 2. 진행

- 위 표를 근거로 의존성 역순으로 옮긴다. 순서를 정한 근거를 이동표에 남긴다.
- 이력 보존이 가능한 파일은 `git mv`를 쓴다.
- 이동 / import 정합 / 이름 개정 / 코드 품질 정리를 **추적 가능한 조각**으로 나누고 조각마다 시험한다.
  대이동을 한 번에 한 뒤 오류를 추측으로 고치지 않는다.
- 파일을 열어 옮길 때 이름·책임·분기·중복·죽은 코드·조용한 실패·주석을 함께 본다.
  위반이 없으면 억지로 바꾸지 않고 "통과" 근거를 남긴다.
- 옛 구조를 살리는 무기한 별칭·호환 shim·중복 import 경로를 만들지 않는다. 명시적인 이행 계약이 없으면
  생산자와 소비자를 같은 조각에서 새 경로로 옮기고 옛 경로 검색 결과 0을 만든다.

## 3. 바이트가 계약인 파일

프롬프트·스키마·직렬화 형식처럼 바이트나 형태 자체가 계약인 파일은 이동 전후 **바이트 동일** 또는
명시적인 계약 diff를 증명한다. 과거 spec·기록 문서는 "현재화"한다는 이유로 고쳐 쓰지 않는다.

## 4. 삭제

소비자 0을 코드·동적 로딩·문서 명령·CI·외부 runner까지 확인한 뒤 지운다.
대용량이거나 되돌리기 어려운 삭제는 실행 직전에 범위를 보고한다.

## 5. 완료

빌드 통과가 아니라 다음을 모두 통과해야 완료다.

- 단위 전수, 계약 시험
- 실제 기동과 대표 끝까지 검증(`e2e-verify`), 해당되면 UI
- CI
- 옛 경로·옛 이름 검색 결과 0
- 이동 전 기준선과 동작 동일
