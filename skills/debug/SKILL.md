# 디버깅 — 원인을 확정하고 고친다

근본 원인·관측 지점 먼저·폴백 금지·옛 이름 0은 헌법 §3, 판정 원칙은 헌법 §2다. 이 스킬은 **원인을 찾아 확정하고
고치는 절차**만 갖는다. 실제 경로 끝까지 검증은 `e2e-verify`가 맡는다.
실행 명령·포트·로그 위치·저장소 경계·SDD 위치는 프로젝트 `CLAUDE.md`를 따른다. 프로젝트 도메인 스킬이 같은 일을
더 좁게 정의하면 그 스킬이 이긴다. **순서를 뒤집지 않는다** — 원인을 먼저 찍지 않고 배선도를 깐 뒤 실제 값을 흘린다.

## 1. 진행 순서

```
0) 의도 복원   요구·포함/제외·제약·성공 조건. 사용자가 말한 원인은 가설로 따로 둔다
1) 현장 보존   저장소마다 branch·HEAD·WIP, 실행 중 서비스, 재사용할 기준선·봉인 결과
2) 증상 고정   통계·인상이 아니라 틀린 결과 하나의 좌표(입력 위치·객체 id·응답)
3) 배선도      입력부터 최종 소비자까지 전 구간. 고리마다 함수명 + 파일:행
4) 값 흘리기   그 좌표의 실제 값을 배선도 위로 흘려 첫 어긋난 고리를 찾는다
5) 원인 확정   원인 꼬리표(§4)에 빈칸이 없어야 확정. 못 채우면 관측 지점을 넣고 4)로
6) 영향도      같은 계약의 생산자·소비자 전부를 표로(§6)
   ── 「조사만」「고치지는 말고」「이거 지워도 돼?」면 여기서 정지 ──
7) 수정        의도·수용 기준을 기록한 뒤 근본 원인 한 곳을 고친다(§7)
8) 점진 검증   가장 가까운 검사부터 넓혀 간다(§8)
9) 보고        §9
```

요청에 포함된 되돌릴 수 있는 변경은 9)까지 이어서 한다. 새 범위·비용·외부 동작이 생길 때만 묻는다.
**정지 요청이면 제품 코드를 한 줄도 바꾸지 않는다.**

| 유형(둘 이상이면 전부) | 두꺼워지는 곳 |
|---|---|
| 버그(있던 것이 잘못 동작) | 4)~5) — 첫 어긋난 고리와 꼬리표 |
| 기능(없던 것을 만든다) | 3)·7) — 의도·수용 기준을 먼저 적고 빈 자리를 배선도에 표시 |
| 리팩터링(동작은 두고 구조만) | 3)·6) — 기준선 고정 → 이동표 → 의존성 역순 → 옛 경로 0. [리팩터링](references/refactoring.md) |
| 느림(성능) | 2)·4) — 시간을 재는 관측 지점부터(§5 「느림」) |

## 2. 배선도

- 입력 → 파싱·검증 → 도메인 로직 → 저장·캐시 → API·이벤트 → 소비자 상태 → 화면(최종 산출)까지 영역별로 깐다(지목된 조각만 보지 않는다).
- 최종 출력에서 입력 쪽으로, 입력에서 출력 쪽으로 **양방향**으로 확인한다.
- 코드 경로만 보고 "전달됐다", "DB에 썼다"고 가정하지 않는다. 실제 기록을 연다.
- 코드 인덱스(codegraph 등)가 최신이면 호출자·소비자 추적에 grep보다 먼저 쓰되, 결론은 원문으로 확인한다.

## 3. 값 흘리기

고른 좌표 하나에 대해 고리마다 네 값을 채운다. 시간 순서와 상태 변화도 적는다.

```text
들어온 실제 값 → 어떤 코드가 어떻게 바꿨나 [파일:행] → 나간 실제 값 → 다음 소비자가 어떻게 썼나 [파일:행]
```

- 기대값은 기억이 아니라 **원문·현행 계약·봉인된 정답지**에서 가져온다.
- 값을 볼 수단이 없으면 되돌릴 수 있는 관측 지점(구조화 로그·중간 산출물 저장)을 먼저 만든다.
- 외부로 나가는 요청(API·쿼리·LLM 프롬프트)은 템플릿이 아니라 **실제로 직렬화되어 나간 바이트**를 연다.

## 4. 원인 꼬리표 — 사슬이 끊기면 원인이 아니다

```
증상 ← 이 값이 여기서 나왔다 [파일:행] ← 여기서 바뀌었다 [파일:행] 들어온 값→나간 값
     ← 여기서 들어왔다 [파일:행] ← 최초 입력 [파일:행]   ⇒ 추적 순서(§5)의 몇 번인가
```

확정하려면 다음이 모두 있어야 한다.
- 최초의 올바른 입력 좌표와, 처음 잘못된 값이 생긴 함수·파일:행
- 그 고리의 들어온 값과 나간 값(관찰한 실제 값)과 증상까지 이어지는 하류 소비자
- 다른 주요 가설을 배제한 검사(로그·최소 재현·역실험)
- 고치면 바뀔 좌표와 바뀌지 않을 범위의 예측

**추측으로 메운 고리가 하나라도 있으면 원인 미확정이다.** 사용자·인계·문서가 말한 원인도 이 사슬을 통과해야 원인이다.

## 5. 원인 추적 순서 — 틀린 좌표 하나에서 앞부터, 외부 의존은 마지막 용의자다

| 순 | 확인 대상 | 여기서 발견되는 결함 |
|---|---|---|
| 1 | 입력 원문 | 애초에 입력이 그렇게 생겼는가 |
| 2 | 구조화 산출(파서·로더·역직렬화) | 원문의 사실이 중간 표현에 실재하는가 — 누락·범위·부모 오귀속 |
| 3 | 결정론 조립·변환(규칙·매핑·병합·필터) | 분기·의무 항목·증거 — **결과 0건·누락은 대개 여기** |
| 4 | 실제로 나간 요청 | 준 줄 알았던 것과 실제로 간 것이 다르다 |
| 5 | 정보 충분성 | 그 입력만으로 사람도 못 푸는가 → 고칠 곳은 2·3 |
| 6 | 검사기·정답지·집계 | **제품이 맞고 판정 쪽이 틀렸을 수 있다** |
| 7 | 외부 의존(모델·라이브러리·서비스·하드웨어) | 위 여섯이 깨끗할 때만 |

**수치가 이상하면 제품보다 검사기(6)를 먼저 연다.** 1~6에서 걸렸는데 7(모델·프롬프트·외부 설정)을 고치면 땜빵이다.
검사기가 틀렸으면 제품을 억지로 바꾸지 않고 원문 `파일:행` 근거로 정답지·검사 계약을 고친다.

| 관찰 | 결함 위치 |
|---|---|
| 원문엔 있는데 실제 요청에 없다 | 생산·전달(2·3) |
| 요청엔 있는데 지시·계약이 빼거나 왜곡하게 한다 | 요청 계약(4) |
| 입력과 지시가 충분한데 응답이 틀렸다 | 외부 의존 한계 후보(7) — 반례를 확보한 뒤에만 |
| 응답은 맞는데 후단에서 사라지거나 바뀐다 | 스키마·정규화·저장·표시 |
| 근거 없는 결과가 통과하거나 정답지와 원문이 다르다 | 검증기·정답지(6) |

**검사기를 먼저 의심할 것**: 집계 단위 혼동(발생/고유/상위 묶음) · 좌표계(행/문자, 0/1 기준) · 다른 입력 해시나 낡은
기준선 · 옛 계약으로 만든 정답지 · 정상 종결(제외·외부)을 실패로 합산 · 이전 세대 결과를 읽음 · 모집단 범위 차이.

**조사 수단은 싼 것부터**: 기존 증거(봉인 해시·로그·지난 결과) → 원문 코드와 생산자·소비자 → 영향 좌표 →
집중 로그·계측 → 최소 재현·역실험 → git 이력·bisect → 공식 소스·문서.

**느림**: 추측으로 최적화하지 않는다. 단계별 시간·호출 수·대기·동시성을 재서 **임계 경로**를 찾는다. 전후 비교는 같은
입력·환경·캐시 상태에서, 대표 규모로 한다. 상한·건너뛰기·자르기·조용한 재시도로 속도나 성공률을 꾸미지 않고
같은 일을 두 번 하는 경로부터 없앤다.

## 6. 영향도 — 이 표 없이 고치지 않는다

| 축 | 확인할 것 |
|---|---|
| 이름 | 함수·타입·필드·라벨·관계·경로·이벤트·환경변수의 현재 이름, **옛 이름**, 동의어, 직렬화 키 |
| 생산 | 값·이벤트·파일·레코드를 처음 만드는 코드와 입력(파서·빌더·어댑터·모델 출력) |
| 변환 | 검증기·매퍼·정규화·직렬화·투영·프롬프트·병합 |
| 저장 | DB 스키마·라벨·속성·관계, 캐시·인덱스·파일·manifest, 전역 상태, migration |
| 계약 | 함수 시그니처, API, IPC, 이벤트, 큐, CLI, JSON schema, 오류 형식 |
| 소비 | 호출자, 백엔드, 프런트 상태·UI, 외부 runner, 배치, 문서에 적힌 명령 |
| 실행 환경 | config, env, port, feature flag, profile, submodule, provider·model, 배포·CI |
| 검증 자산 | 단위·통합·E2E 테스트, fixture, 정답지, mock, 스크린샷, 벤치마크 |
| 실패 수명주기 | 빈값·잘못된 입력·중복, 재시도, 취소, timeout, 종료, rollback, 재실행 |
| 저장소 경계 | 바뀌는 독립 저장소, 적용 순서, **사용자 WIP** |

- 이름·동의어·옛 이름·직렬화 필드·import·route·쿼리를 **저장소 경계 밖 소비자까지** 검색한다. 동적 로딩·레지스트리·
  설정·CI·외부 runner도 본다.
- 삭제는 이 범위에서 **소비자 0을 증명**한 뒤 한다. "영향 없음"도 검색 범위와 근거를 남긴다.
- 전수 확인이 불가능하면 범위와 미검증 소비자를 적고 완료 판정에서 뺀다.

## 7. 수정

- 고치기 전에 의도·수용 기준·영향 생산자/소비자·검증 방법을 프로젝트가 정한 곳(spec·이슈·인계)에 적는다(헌법 §3).
  디버깅용 관측 코드도 변경이다 — 목적과 되돌림 방법을 짧게 적는다.
- **한 조각 = 원인 하나 + 그 계약의 양끝.** 파일 한 개가 아니라 책임 한 개가 단위다. 생산자와 소비자를 같은 조각에서 바꾼다.
- 의미 판단은 의미 계층이, 구조·조립·검증은 결정론 계층이 맡는다. 서로의 결손을 덮지 않는다.
- 특정 샘플·고객·프레임워크 문자열에 맞춘 공용 로직, 임의 상한·skip, 옛 이름 별칭을 만들지 않는다.
- 수정할수록 분기·맵·병합이 늘면 멈추고 설계를 다시 본다. 삭제한 코드를 주석으로 남기지 않는다.
- 이동·이름 변경·동작 변경을 한 덩어리로 섞지 않는다 — [리팩터링](references/refactoring.md).

## 8. 점진 검증 — 빠르게와 깊게는 맞바꾸지 않는다

```text
변경 직후  → 고치기 전 실패를 재현하던 가장 가까운 단위·계약 검사
조각 완료  → 영향 저장소의 회귀와 실제 작은 입력 하나
통합 완료  → 실제 생산자→소비자 사슬 한 번(mock 아님)
최종 합격  → 요구된 전체 규모의 끝까지 검증 한 번 — e2e-verify
```

반복 실행 절약은 헌법 §6(같은 해시·커밋 재실행 금지, 회귀는 끝난 뒤 한 번). 도구가 스스로 빌드하면 수동 선행 빌드를 하지 않는다.
**줄이면 안 되는 깊이** — 수정 직후 반증한다.

- 고치기 전 실패가 같은 입력에서 사라졌고 기존 정상 입력은 그대로 통과하는가.
- 빈값·잘못된 입력·경계·중복·순서 변화·재시도·부분 실패·종료에서도 맞고, 실패 경로가 정상 결과를 덮지 않는가.
- 테스트가 그 실패·경계 조건을 실제로 assert하는가(테스트 코드를 읽는다).
- 영향도 표의 모든 축이 검증 항목에 실제 값으로 한 번 이상 나타나는가. 안 나온 축은 미검증.
- **실패하면 다음 패치로 덮지 않고 현재 조각에서 원인을 끝낸다.**

## 9. 보고와 종료 조건

- 첫 문단: 원인(추적 순서 몇 번, 결함 위치) · 무엇을 고쳤나 · 검증 결과. 정지 요청이었으면 "제품 코드 변경 없음".
- 이어서 원인 꼬리표, 영향도 표(검색 범위 포함), 검증 항목별 기대/실제/판정(헌법 §2의 네 라벨, 해당 없음엔 이유).

다음이 모두 0이어야 끝난다: `파일:행`이 빈 배선 고리 · 추측으로 메운 꼬리표 고리 · 검색 범위·근거가 없는 영향 축 ·
검증에 안 나왔는데 미검증으로 안 적은 축 · 옛 이름·옛 경로 검색 결과 · 실행 안 하고 검증됨으로 적은 항목.
