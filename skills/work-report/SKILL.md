# 주제별 작업보고

## 한 파일 안에 함께 있어야 하는 것

**실제 전달한 프롬프트 → 그 요구로 한 일 → 결과·남은 DoD**를 같은 날짜 보고 파일 안에서 읽을 수 있어야 한다.
프롬프트만 남기거나, 한 일을 외부 상세 링크로 대신하거나, 스킬 이름만 나열하면 보고가 아니다.

| 순서 | 내용 |
|---|---|
| 1. 전달한 프롬프트 | 사용자가 실제 전달한 업무 프롬프트 원문. 다듬은 지시문·요약을 원문이라 쓰지 않는다. 없으면 「미확보」로 밝히고 재구성하지 않는다. 길면 `<details>` 접기(지원 안 하면 본문 뒤 부록). 후속 지시는 원문과 구별한다 |
| 2. 주제별 작업내용 | 제목만 봐도 무슨 업무인지 알게. 요구/DoD 번호 → 실제 한 일·산출물 링크 → 전후·판정·남은 일 |
| 3. 스킬 보강 | 클릭 가능한 스킬 이름(`SKILL.md` 링크, 필요하면 참조 파일) → 기존 문제 → 바뀐 행동. 「몇 개 보강」만 쓰지 않는다 |
| 4. 미완료 | 남은 요구와 확인할 것. 여러 주제에 걸친 미결만 여기 모으고, 주제 하나의 다음 할 일은 그 주제 끝에 둔다 |

보고를 줄이거나 옛 구성으로 되돌릴 때도 이 넷은 남긴다. 되돌릴 판에 최근 요구가 없으면 다시 반영한다.

## 입력과 저장

먼저 프로젝트 `CLAUDE.md`에서 **보고 위치·보고 단위·보호 경계·보고 근거 규칙**을 찾는다. 그다음 요청한 날짜·독자·양식,
기존 보고 전문, 변경·검증 근거를 읽는다. 보고 작성은 새 실험·유료 실행·외부 게시 권한이 아니다.

- 저장 위치: 프로젝트 `CLAUDE.md` → 사용자 지정 → 둘 다 없으면 묻는다.
- 여러 프로젝트가 같은 보고 위치를 쓰면 날짜별 `YYYY-MM-DD.md` 하나에 합친다. 프로젝트마다 보고 폴더를 따로 만들지 않는다.
- 저장 전에 파일명과 본문 날짜로 기존 보고를 찾는다. 있으면 제목·결론·본문을 당일 주제별로 통합하고, 없을 때만 새로 만든다.
  같은 날 새 작업을 별도 보고로 붙이거나 마지막 작업으로 기존 내용을 덮지 않는다. 사용자 WIP를 피하려고 같은 날 보고를 따로 만들지 않는다.
- 사용자가 기존 구성이 낫다고 했으면 그 구성에서 필요한 내용만 고친다. 위치 통합을 이유로 링크 목록·프로젝트별 요약판으로 다시 만들지 않는다.
- 여러 기존 보고를 합칠 때는 내용·근거를 대조하고 원본은 보관한다. 이관한 과거 상세 보고는 근거로 남기고 새 보고에서 링크한다.
- 당일 업무는 실제 요청·수행 근거로 정한다. 파일명 날짜나 같은 폴더라는 이유로 과거·다른 업무를 넣지 않는다. 파일 이관과 제품 작업을 구별한다.
- 중간 보고는 진행 중이라고 표시한다. 단순 상태 질문에는 파일을 만들지 않는다.

## 쓰는 법

- 원문 요구·DoD 순서에 번호를 맞춰 `프롬프트의 요구 | 실제 한 일·산출물 | 판정·남은 일`로 대응시킨다. 원문에 없던 번호는 보고용이라고 밝힌다.
  한 요구가 여러 산출물로, 여러 요구가 한 작업으로 이어지면 같은 행에서 잇는다.
- **판정은 실제 결과가 합격선을 넘는지로 한다.** 「작성·실행했다」는 작업내용이지 근거가 아니다. 기준과 다르면 미충족, 증거가 없으면 미검증·대기.
- 후속 지시로 바뀐 범위·방향은 원문을 덮지 말고 해당 행에 변경 근거와 현재 조건을 적는다. 원래 업무와 나중에 붙은 스킬 정비를 구별한다.
- 주제 하나의 이유·변경·결과·미결은 그 자리에서 끝낸다. 왜/목적/어떻게/결과를 각각 긴 절로 나눠 같은 주제를 네 번 쓰지 않는다.
  필요하면 목적 한 문장과 `항목 | 전 | 후·현재` 표 하나. 대응표와 전후 표가 겹치면 하나로 합친다.
- 표 한 칸에 여러 문단을 넣지 않는다. 같은 사실을 결론·표·다음 할 일에서 반복하지 않는다.
- 여러 프로젝트면 프로젝트별로 나누되 같은 공용 스킬 작업을 양쪽에 반복하지 않는다.
- 한두 화면을 우선하되 의미·수치·제약을 잘라 길이를 맞추지 않는다. 반복부터 없애고 상세는 링크한다.
- 처음 보는 사람이 읽을 말로 쓴다. 전문 용어는 그 자리에서 짧게 푼다. 진행 과정·자기 해설·방어 문장·소감은 뺀다.
- 전후 수치는 같은 입력·단위·범위로 비교한다. 나빠진 결과도 쓴다. 변경 전을 못 봤으면 출처(사용자 설명·과거 기록·미확인)를 표시하고 옛 구현을 지어내지 않는다.
- 판정을 가르는 입출력·화면은 필요할 때만 짧게 발췌하고 전체 근거를 링크한다. 로컬 경로를 공유 가능한 URL처럼 쓰지 않는다.

**무엇을 근거로 삼는지는 프로젝트 `CLAUDE.md`의 보고 근거 규칙을 따른다**(예: 변경 보고는 git 기록 확인, 제작 수량과 실제 사용 완주 구분).
현행 명세(spec)가 정본이면 그 명세로 검증된 범위만 표현한다. 규칙이 없으면 이 문서의 공통 기준만 쓴다.

## 형식

기존 양식을 우선한다. HTML은 화면 공유·접기·인쇄가 필요하거나 사용자가 고를 때만 만들고, 같은 내용의 정본을 따로 두지 않는다.
만들면 실제 렌더와 링크를 확인한다. 형식보다 정보 구조를 먼저 정리한다.

## 저장 후 검토

**사용자에게 줄 날짜별 파일 자체를 다시 열어** 원문·수정 전 보고와 대조한다.
1. 프롬프트 원문이 같은 파일에 있고 각 요구가 한 일·판정과 이어지는가?
2. 요청한 핵심 업무가 본문에 있는가? 빠진 것을 링크로 대신하지 않았는가?
3. 스킬 이름이 클릭되고 그 `SKILL.md`·참조 파일이 실제로 있는가?
4. 압축·복원·이동으로 최근 요구·기존 결과·미검증을 잃지 않았고, 안 한 업무가 섞이지 않았는가?
5. 같은 사실이 반복되지 않고, 날짜별 정본이 하나인가?

하나라도 아니면 완료라고 답하지 말고 그 파일을 고친다. 다른 파일이나 스킬을 고친 것으로 오늘 보고 반영을 주장하지 않는다.

## 다른 스킬로

보고 중 확정된 방향·재개 정보는 handoff로 넘긴다(보고서를 인계로 쓰지 않는다). 실행 프롬프트 작성은 task-prompt, 월간 연구노트는 research-note.
프로젝트에 전용 도메인 스킬(자료 불일치 감사·발표자료 등)이 있으면 프로젝트 `CLAUDE.md`가 가리키는 것을 쓴다.
