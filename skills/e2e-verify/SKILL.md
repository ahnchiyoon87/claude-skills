# 끝까지 검증 — 실제 경로를 완주하고 증거로 판정한다

"실행한 것만 됐다"·판정 라벨·"검사는 깨뜨려 본다"는 헌법 §2, 검증 1회·10분 사전 알림은 헌법 §6이다.
이 스킬은 **실제 경로를 끝까지 검증하는 절차**만 갖는다. 원인 추적·수정은 `debug`가 맡는다.
서비스 기동·포트·로그 위치·테스트 계정·격리 DB는 프로젝트 `CLAUDE.md`를 따른다. 프로젝트 정답지·DB read-back·
전용 runner가 있으면 그 프로젝트 스킬이 세부를 소유한다.
**검증 요청만 받았으면 제품을 고치지 않는다.** 읽기·실행·판정까지 하고, 결함은 `debug`로 넘긴다.

## 1. 착수 — 돌리기 전에 읽는다

1. 대상 저장소마다 branch·HEAD·WIP를 확인하고 사용자 WIP를 분리한다.
2. 최근 결과 파일·실패 단계·스크린샷·로그를 **먼저** 읽는다. 아무것도 안 보고 전체 실행부터 돌리지 않는다.
3. **검증 범위를 봉인한다.** 비면 실행하지 않는다.

```yaml
commit: 저장소별 HEAD (dirty 여부 포함)
input: 입력 원문·데이터 경로와 해시
config: 설정·계약·프롬프트 경로와 해시
runtime: 외부 서비스·모델·버전
run: 이번 실행 하나의 결과 폴더 (latest 같은 별칭 금지)
database: 명시한 격리 DB (공유·운영 DB 금지)
consumers: 확인할 최종 소비자 (API·UI·파일)
axes: 이번에 판정할 층 (구조 / 실행 / 의미)
```

범위가 다른 두 실행을 비교하지 않는다. 마지막 관련 변경 **이후**의 실행만 유효하고, 지난 수치·문서는 이번 증거가 아니다.

## 2. 3층 검증

세 층은 서로를 대신하지 못한다. 요구된 층이 다 돌아야 검증됨이고, 안 돈 층은 미검증이다.

| 층 | 묻는 것 | 방법 | 이것만으로 말할 수 없는 것 |
|---|---|---|---|
| **구조** | 결정론으로 셀 수 있는 것이 계약대로인가 | 자동 시험과 **전수 회계** — 필수 항목마다 누락·중복·예상 밖·미분류 0을 코드로 센다 | 실제 경로가 도는지, 뜻이 맞는지 |
| **실행** | 실제 경로가 끝까지 도는가 | mock 아닌 실제 서비스·DB·UI에서 같은 건을 입력→처리→저장→API→화면까지 따라간다 | 결과의 뜻이 원문과 같은지 |
| **의미** | 결과가 원문·요구의 뜻과 같은가 | 결과보다 먼저 봉인한 표본을 **주 에이전트가 직접** 원문과 대조(§4) | 표본 밖 모집단 |

- 결정론으로 판정할 수 있는 것은 전부 코드로 센다. 검사기가 없으면 검사기 작성이 선행이고, 그 전까지 그 축은 미검증이다.
- 검사를 만들거나 고치면 일부러 틀린 입력·fixture로 깨뜨려 잡히는지 확인한다(헌법 §2).
- 정상 종결(제외·외부 등 계약상 정상 상태)과 실패를 섞지 않는다.
- 의미 판정에 검증용·심판 모델을 부르지 않는다. 문자열·개수 일치·문법 통과는 의미 정확도가 아니다.

| 점검(해당 없으면 이유와 함께 해당 없음) | 증거 |
|---|---|
| E1 정상 | 실제 입력과 출력 |
| E2 실패 | 틀린 입력이 계약된 오류(좌표 있는 메시지)로 끝나는가 |
| E3 경계 | 빈값·0·최대·중복·순서·재실행 |
| E4 수명주기 | 취소·재시도·부분 실패·종료·재시작 |
| E5 회귀 | 수정 전 실패가 재현 시험으로 닫혔는가 |
| E6 기존 정상 | 관련 기존 시나리오 통과 |
| E7 시험 실효성 | 시험이 실패·경계를 실제로 assert하는가(시험 코드를 읽는다) |
| E8 계약 양끝 | 생산자와 소비자를 실제 값으로 연결 |
| E9 화면 | 실제 화면·console·network·상태 변화 — [화면 검증](references/ui-verification.md) |
| E10 데이터 | 원문과 최종 저장값·응답을 건별 대조(개수만 맞는 것은 정확성이 아니다) |

## 3. 네 칸 기록

검증 항목마다 채운다. 한 칸이라도 비면 그 항목은 검증되지 않았다.

```text
입력: 실제 값 또는 봉인한 참조·해시
중간: 거쳐 간 생산자→소비자 관문과 그 지점의 실제 값
결과: 실제 출력·저장값·화면
판정: 기대값(출처)과의 차이와 근거 → 검증됨 / 실패 / 미검증 / 해당 없음
```

## 4. 의미 표본 — 결과보다 먼저 고르고 봉인한다

- **정답지는 결과보다 먼저**, 원문(소스·DDL·요구 문서)에서 뽑아 봉인한다. 결과를 이미 봤다면 기록하고 구조 정보로 다시 고른다.
- **구조 정보만 보고** 복잡·중간·단순(음성 대조 포함), 정상·실패·경계, 종류·모듈·언어·데이터 접근 형태로 층화한다.
- 크기: 변경 중 집중 검증 10~20개(영향받은 종류 포함), 최종 승인 30~40개, 한 종류 20개 이하, 모집단이 작으면 그 종류는 전수.
  프로젝트가 정한 수가 있으면 그것. 사용자가 더 적게 요구하면 그만큼 봉인하고 나머지는 미검증.
- 결과를 본 뒤 쉬운 표본으로 바꾸지 않는다.
- 표본마다 한 행: 원문 근거 → 기대 의미 → 실제로 들어간 입력 → 출력 → 최종 저장값 → 판정.
- 판정은 하나만: `exact`(표현은 달라도 범위·방향·극성·대상·순서가 같음) · `partial` · `contradiction` ·
  `fabrication`(근거 없는 의미 추가) · `omission`(결과를 바꾸는 조건·효과 누락) · `needs_context`(입력에도 근거 없음).
  예: "부족"을 "없음"으로, `<`를 `<=`로 바꾸면 의미 오류다.
- **표본 결과는 표본에만 유효하다.** 모집단 전체에 대해 말할 수 있는 것은 구조층 전수 결과뿐이다.

## 5. 실패 분류와 좁히기

| 분류 | 예 | 넘기는 곳 |
|---|---|---|
| 제품 로직 | 계약과 다른 출력, 누락·중복 | `debug` |
| 검증 도구(selector·동기화·대기) | 요소를 못 찾음, 준비 전 클릭 | 검증 스크립트 수정 |
| 정답지·검증 규칙 | 원문과 다른 기대값, 낡은 계약, 집계 단위 혼동 | 원문 근거로 정답지 수정(`debug` 추적 순서 6번) |
| 환경·서비스 수명주기 | 서비스 미기동, 포트 충돌, 인증, 격리 DB 상태 | 환경 복구 후 재실행 |

근거는 실패 단계·스크린샷·console·network·서버 로그·입력 해시. 분류 못 한 실패는 0이어야 한다.

**좁히는 사다리** — 가장 작은 단위부터. 깊이(입력→처리→저장→화면)는 줄이지 않는다.

1. 재처리 없이 이미 나온 결과만 다시 검사한다(결과·그래프·정답지만 의심될 때).
2. 앞 단계 결과를 유지한 채 화면 동선만 다시 돈다(selector·동기화만 의심될 때).
3. 제품 수정이 필요하면 해당 저장소의 국소 단위·계약 시험을 먼저 통과시킨다.
4. 전체 재실행은 입력·처리 파이프라인이 바뀌었거나, 앞 단계 결과의 지문이 없거나 달라졌거나,
   국소 수정이 모두 통과해 최종 통합 증명이 필요할 때만.

## 6. 실행 규율

- **같은 대상의 실제 경로 검증은 한 세션·한 에이전트가 소유한다.** 같은 완주를 여러 에이전트에 나누면 공유 DB·포트·프로세스가
  충돌하고 증거가 섞인다. 환경 점검(doctor류)은 상태가 미확정일 때 한 번.
- 기본 개발 DB·공유 DB·기존 사용자 프로세스를 지우거나 덮지 않는다. 검증 전용 격리 자원과 runner 소유 프로세스만 쓴다.
  포트 번호만 보고 다른 프로세스를 종료하지 않는다. 검증 쿼리에 쓰기·삭제·제약 변경을 넣지 않는다.
- 증거: 실행 명령, run id, 결과 파일, 로그, 스크린샷, 입력·설정 해시, 커밋. 대화에는 건수와 첫 실패만, 전체 실패 목록은
  해시가 있는 파일에 둔다. 실패는 `파일:행` 또는 키로 적는다.
- 진단용 리허설·headless·권한 우회·mock 산출물은 최종 증거로 승격하지 않는다. 기능 E2E 통과와 발표 영상 완성은 별개다.

## 7. 판정과 보고

라벨은 네 개만 쓴다.
- 검증됨: 입력·중간·결과·기대값 대조가 모두 있다
- 실패: 실제 결과가 봉인한 계약·정답과 다르다
- 미검증: 환경·권한·증거·도구가 없어 실행하지 못했다(이유와 필요한 조건)
- 해당 없음: 현행 계약상 대상이 아니다(이유)

필수 축 하나라도 실패·미검증이면 전체 완료를 선언하지 않는다. 결과에 맞춰 기대값을 낮추지 않는다.
완료 판정 전에 요구를 거꾸로 대조한다(헌법 §3) — 요구 / 기대 결과 / 구현 위치 / 실제 실행·산출물 근거 / 판정 표.

보고 순서: 결론 한 줄 → 검증됨(입력·명령·실제 수치·기대 대조) → 실패(첫 불일치 키·`파일:행`·하류 영향) →
미검증(안 잰 축·이유·필요 조건) → 보존(손대지 않은 DB·WIP·범위 밖 서비스) → 증거 경로.

다음이 모두 0이어야 끝난다: 네 칸 중 빈칸 있는 항목 · 판정 없는 시나리오 · 분류 안 된 실패 · 안 돌렸는데 미검증으로
안 적은 축 · 결과를 본 뒤 고른 의미 표본 · 리허설·headless·mock을 최종 증거로 쓴 것.
